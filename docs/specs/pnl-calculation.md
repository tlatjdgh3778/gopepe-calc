- 상태: 완료

## 1. 목표
사용자가 심볼(BTCUSDT·ETHUSDT·SOLUSDT), 방향(롱·숏), 레버리지를 고르고 진입가·종료가·수량을 넣으면, USDT 마진 무기한 선물 포지션의 필요 증거금·손익·ROE가 계산 버튼 없이 `/` 화면에 바로 표시된다. 같은 입력이면 Bybit 계산기와 같은 결과를 낸다. [제안 후 승인] 통합 요구(직접 작성 파일 기준 `"use client"` 범위는 [사용자 결정], 나머지는 [제안 후 승인]: shadcn `input`·`label`·`select`·`toggle-group`·`card` 추가, 직접 작성하는 파일 중 `"use client"`는 `components/pnl-calculator.tsx` 하나만 두고(shadcn이 생성한 파일의 지시문은 생성 결과대로 둔다) `app/page.tsx`는 h1 하나를 가진 동기 컴포넌트로 유지, 상태는 로컬 `useState`, `globals.css`에 라이트·다크 `--profit`·`--loss` 토큰 추가, 다크 변형을 `.dark` 클래스 대신 `prefers-color-scheme: dark` 미디어 쿼리로 켜기, devDependency `@testing-library/user-event` 추가와 `bun.lock` 커밋, 모든 입력에 label 연결, 결과 영역 `aria-live="polite"`, 런타임 의존성은 shadcn 컴포넌트가 요구하는 것만 추가, 네트워크 리소스 미사용, 숫자는 decimal 라이브러리 없이 JS `number`로 계산)는 계획의 Task 완료 조건으로 확인한다. → F-7(`docs/specs/input-validation.md`) 4장 공용 모듈·탭 구조가 `"use client"` 한 파일(`components/pnl-calculator.tsx`) 조건과 h1 하나만 가진 동기 `app/page.tsx` 조건을 완화한다.

## 3. 완료의 정의
- DoD-1: `calculatePnl`의 `initialMargin`은 진입가 × 수량 ÷ 레버리지의 반올림하지 않은 값이다 — 검증: 단위 테스트 [제안 후 승인]
- DoD-2: 롱의 `pnl`은 (종료가 − 진입가) × 수량이다 — 검증: 단위 테스트 [제안 후 승인]
- DoD-3: 숏의 `pnl`은 (진입가 − 종료가) × 수량이다 — 검증: 단위 테스트 [제안 후 승인]
- DoD-4: `roe`는 `pnl` ÷ `initialMargin` × 100(%)이다 — 검증: 단위 테스트 [제안 후 승인]
- DoD-5: 아래 Bybit 기준 사례 C1~C6 각각에서 `calculatePnl` 원값을 DoD-18 규칙과 DoD-20 자릿수로 표시한 숫자가 표의 Bybit 표시값과 같다 — 검증: 단위 테스트 [사용자 결정]
- DoD-6: `qtyFromValue`는 USDT 금액(포지션 가치) ÷ 진입가를 돌려준다 — 검증: 단위 테스트 [사용자 결정]
- DoD-7: `formatUsdt`는 천 단위 구분, `decimals` 옵션의 소수 자릿수(기본 2, DoD-18 규칙), ` USDT` 단위를 붙이고, `signed` 옵션이 켜지면 양수에 `+`, 음수에 `−`(U+2212)를 붙인다(예: `formatUsdt(1234.56789, { signed: true, decimals: 4 })` → `+1,234.5678 USDT`) — 검증: 단위 테스트 [사용자 결정]
- DoD-8: `formatPercent`는 소수 둘째 자리(DoD-18 규칙)에 `%`와 부호(양수 `+`, 음수 `−`(U+2212))를 붙인다(예: `+12.35%`) — 검증: 단위 테스트 [제안 후 승인]
- DoD-9: `/` 첫 화면의 초깃값은 심볼 BTCUSDT, 방향 롱, 레버리지 10, 수량 단위 코인이고, 진입가·종료가·수량은 비어 있으며 세 결과는 `—`다 — 검증: 컴포넌트 테스트(RTL + user-event, jsdom) [제안 후 승인]
- DoD-10: 진입가·수량·레버리지를 입력하면 계산 버튼 없이 필요 증거금이 부호 없는 형식(DoD-20 자릿수)으로 표시되고, 종료가가 비어 있는 동안 손익·ROE는 `—`다 — 검증: 컴포넌트 테스트 [제안 후 승인]
- DoD-11: 종료가까지 입력하면 손익(`signed` 형식)과 ROE가 즉시 표시된다 — 검증: 컴포넌트 테스트 [제안 후 승인]
- DoD-12: 손익·ROE는 각자의 표시값이 양수면 `--profit`, 음수면 `--loss` 색으로 표시된다 — 검증: 테스트 설계 단계에서 확정 [사용자 결정]
- DoD-13: 수량 단위를 코인 → USDT로 바꾸면 수량 × 진입가가, USDT → 코인으로 바꾸면 금액 ÷ 진입가가 지수 표기·천 단위 구분 없이 소수 최대 8자리로 사사오입하고(DoD-18의 버림은 적용하지 않는다) 끝의 0을 지운 형식(예: `0.2`, `0.00000154`, `7800`)으로 입력란에 채워진다 — 검증: 컴포넌트 테스트 [사용자 결정] → USDT → 코인 전환의 채움 값(금액 ÷ 진입가)은 F-7(`docs/specs/input-validation.md`) DoD-16이 대체한다(코인 → USDT 전환은 그대로다).

## 4. 인터페이스 계약
- `lib/symbols.ts`: `type SymbolInfo = { symbol: "BTCUSDT" | "ETHUSDT" | "SOLUSDT"; baseCoin: "BTC" | "ETH" | "SOL"; marginDecimals: 2 | 3 }`, `export const SYMBOLS: readonly SymbolInfo[]`. `marginDecimals`는 BTCUSDT·ETHUSDT 2, SOLUSDT 3이다([사용자 결정]). F-1은 이 세 필드만 기록하고, 최대 레버리지·틱·수량 단위·최소 수량·기준일은 F-7, 유지증거금률은 F-3이 필드를 추가한다. [제안 후 승인] → F-7(`docs/specs/input-validation.md`) 4장 `lib/symbols.ts`가 대체한다. 유지증거금률 첫 단계(`maintenanceTier`)도 F-3이 아니라 F-7이 기록하고, 전체 단계는 F-10에서 한다.
- `lib/pnl.ts`: `calculatePnl(input: { side: "long" | "short"; leverage: number; entryPrice: number | null; exitPrice: number | null; qty: number | null }): { initialMargin: number | null; pnl: number | null; roe: number | null }`. 반올림하지 않은 원값을 돌려주고, 계산에 필요한 값이 없거나 0 이하이거나 결과가 유한하지 않으면 해당 필드는 `null`이다. [제안 후 승인]
- `lib/pnl.ts`: `qtyFromValue(valueUsdt: number | null, entryPrice: number | null): number | null`. 금액이나 진입가가 없거나 0 이하이거나 결과가 유한하지 않으면 `null`이다. [제안 후 승인]
- `lib/format.ts`: `formatUsdt(v: number | null, opts?: { signed?: boolean; decimals?: number }): string`, `formatPercent(v: number | null): string`. `null`이면 `—`를 돌려준다. [제안 후 승인]
- 함수 이름·파일 위치는 구현 단계에서 바꿀 수 있다. 고정하는 계약은 원값과 `null` 반환, 심볼 최소 필드와 증거금 자릿수, 표시 형식의 별도 모듈 분리다. [제안 후 승인]
- URL은 `/`만 바뀐다. 새 라우트·API는 없다. [제안 후 승인]

## 5. 엣지 케이스와 실패 시나리오
화면에는 어떤 입력에서도 `NaN`·`Infinity`·오류가 나타나지 않는다. [제안 후 승인]

### 5.1 비정상 입력
- EC-1: 레버리지 입력란은 숫자만 받는다. 소수점·쉼표·부호·문자가 하나라도 섞인 변경(붙여넣기 포함)은 통째로 무시되고 직전 값이 유지된다 — 검증: 컴포넌트 테스트 [사용자 결정]
- EC-2: 진입가·종료가·수량·USDT 금액 입력란은 숫자와 소수점 하나만 받는다. 쉼표·부호·문자·두 번째 소수점이 하나라도 섞인 변경(붙여넣기 포함)은 통째로 무시되고 직전 값이 유지된다 — 검증: 컴포넌트 테스트 [사용자 결정]
- EC-3: 값이 비어 있거나 소수점 `.`만 있거나 0이면 그 값이 필요한 결과만 `—`로 표시하고 0으로 나누지 않는다 — 검증: 단위 테스트(`null` 반환) + 컴포넌트 테스트 [사용자 결정]
- EC-4: 레버리지가 심볼 최대치를 넘어도 계산 결과를 표시하고 경고하지 않는다 — 검증: 컴포넌트 테스트 [제안 후 승인] → F-7(`docs/specs/input-validation.md`) DoD-9·DoD-10이 대체한다(경고를 표시하고 결과는 계속 표시한다).

### 5.2 결과 경계
- EC-5: 진입가와 종료가가 같으면 손익은 `0.0000 USDT`, ROE는 `0.00%`로 부호 없이 표시한다 — 검증: 단위 테스트 [사용자 결정]
- EC-6: 표시 자릿수에서 버린 결과가 0이 되는 값(예: 손익 `-0.00004`, ROE `0.009`)은 원값이 양수든 음수든 부호 없이 0(`0.0000`, `0.00`)으로 표시한다(`+0.00`, `−0.0000` 없음) — 검증: 단위 테스트 [사용자 결정]
- EC-7: 큰 값(예: 수량 1e9)도 천 단위 구분 형식으로 표시한다 — 검증: 단위 테스트 [제안 후 승인]
- EC-8: 계산 결과가 유한한 수가 아니면 해당 결과를 `—`로 표시한다 — 검증: 단위 테스트 [제안 후 승인]
- EC-12: 표시값이 0(`0.0000 USDT`, `0.00%`)인 손익·ROE에는 이익·손실 색을 붙이지 않는다 — 검증: 테스트 설계 단계에서 확정 [사용자 결정]

### 5.3 입력 상태 전환
- EC-9: 심볼이나 방향을 바꿔도 입력값은 유지되고 결과가 다시 계산된다 — 검증: 컴포넌트 테스트 [제안 후 승인]
- EC-10: USDT 모드에서 진입가가 바뀌면 USDT 금액은 유지되고 코인 수량과 결과가 다시 계산된다 — 검증: 컴포넌트 테스트 [사용자 결정]
- EC-11: 진입가가 비어 있거나 소수점 `.`만 있거나 0인 상태에서 수량 단위를 바꾸면 수량 입력란이 비워진다 — 검증: 컴포넌트 테스트 [사용자 결정]
- EC-13: USDT 모드에서 금액이나 진입가가 비어 있거나 0이어서 코인 수량을 환산할 수 없으면 참고 수량을 `≈ — {기초 코인}`(예: `≈ — BTC`)으로 표시한다 — 검증: 컴포넌트 테스트 [제안 후 승인]
