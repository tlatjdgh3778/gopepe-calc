# 스펙: F-4 최대 진입 수량

- 상태: 완료
- 최종 갱신: 2026-11-25

## 1. 목표
사용자가 `/` 화면의 "최대 수량" 탭에서 심볼(BTCUSDT·ETHUSDT·SOLUSDT)·레버리지·진입가·사용 가능 잔고(USDT)를 넣으면, 그 잔고로 열 수 있는 최대 수량(심볼 수량 단위로 내림)과 그 수량의 포지션 가치가 계산 버튼 없이 바로 표시된다. 수수료는 빼지 않으며, 실제 주문 가능 수량보다 클 수 있다는 고지를 함께 띄운다. [사용자 결정]

## 2. 비목표
- 진입·청산 수수료 예약을 계산에 넣지 않는다(F-8). [사용자 결정]
- 방향(롱·숏) 입력을 두지 않는다. [사용자 결정]
- Bybit 최대 주문 수량(`maxOrderQty`)을 기록·검사하지 않고, 리스크 한도 단계별 허용 레버리지 축소를 계산하지 않는다(F-10). [사용자 결정]
- 새 Bybit 기준 사례를 수집하지 않는다. 기준 사례는 손계산으로 만든다. [사용자 결정]
- 공용 모듈(`lib/input.ts`, `lib/format.ts`, `lib/symbols.ts`, `lib/validation.ts`, `components/fields/`, `components/calculator-layout.tsx`, `components/calculator-tabs.tsx`)과 `lib/pnl.ts`·`lib/liquidation.ts`를 수정하지 않는다. [제안 후 승인]
- 계산기 사이에 입력을 공유하지 않는다. [제안 후 승인]

- DoD-2: `maxQuantity`의 `positionValue`는 `qty × 진입가`의 반올림하지 않은 값이다 — 검증: 단위 테스트 [사용자 결정]

## 4. 인터페이스 계약
- `lib/max-quantity.ts`: `maxQuantity(input: { balance: number | null; leverage: number | null; entryPrice: number | null; qtyStep: number; minOrderQty: number }): { qty: number | null; positionValue: number | null; belowMin: boolean }`. [제안 후 승인]
  - 잔고·레버리지·진입가가 없거나 0 이하이거나 결과가 유한하지 않으면 `qty`·`positionValue`는 `null`, `belowMin`은 `false`다. [제안 후 승인]
  - 내린 수량이 `minOrderQty`보다 작으면(0 포함) `qty`·`positionValue`는 `null`, `belowMin`은 `true`다. [제안 후 승인]
- 한도 판정은 `lib/liquidation.ts`의 `exceedsFirstTier(entryPrice, qty, riskLimitValue)`를 import해 쓴다. [제안 후 승인]
- `components/max-quantity-calculator.tsx`: `MaxQuantityCalculator`(props 없음). [제안 후 승인]
- `app/page.tsx` 탭 항목: `value` `"max-quantity"`, `label` `"최대 수량"`, `content`는 `MaxQuantityCalculator` 요소이고 줄 끝에 꼬리표 `// F-4`를 둔다. [제안 후 승인]
- URL은 `/`만 쓴다. 새 라우트·API는 없다. [제안 후 승인]

## 5. 엣지 케이스와 실패 시나리오
화면에는 어떤 입력에서도 `NaN`·`Infinity`·오류가 나타나지 않는다. [제안 후 승인]

### 5.1 비정상 입력
- EC-1: 레버리지 입력란은 숫자만, 진입가·사용 가능 잔고 입력란은 숫자와 소수점 하나만 받는다. 다른 문자가 섞인 변경은 무시되고 직전 값이 유지된다 — 검증: 컴포넌트 테스트 [제안 후 승인]
- EC-2: 진입가·사용 가능 잔고·레버리지 중 하나라도 비었거나 `.`이거나 0이면 최대 수량·포지션 가치는 `—`이고 최소 수량·한도 경고는 표시되지 않는다 — 검증: 단위 테스트(`null`·`belowMin` `false` 반환) + 컴포넌트 테스트 [제안 후 승인]
- EC-3: 입력은 유한하지만 계산 결과가 유한하지 않으면(예: 잔고 × 레버리지가 부동소수점 범위를 넘는 309자리 잔고 × 레버리지 10, 또는 수량을 내린 값이 넘치는 307자리 잔고 · 레버리지 10 · 진입가 1) 최대 수량·포지션 가치는 `—`다 — 검증: 단위 테스트(`null` 반환) + 컴포넌트 테스트 [제안 후 승인] (예시 교체는 [사용자 결정])

### 5.2 한도·최소 수량
- EC-4: 레버리지가 심볼 최대치를 넘으면 `LeverageField`의 최대 레버리지 경고가 표시되고 최대 수량·포지션 가치는 계속 계산·표시된다 — 검증: 컴포넌트 테스트 [제안 후 승인]
- EC-5: 내린 수량이 0이거나 `minOrderQty`보다 작으면(예: SOLUSDT, 레버리지 1, 진입가 150, 잔고 10 → 원값 0.0666…) 최대 수량·포지션 가치는 `—`다 — 검증: 단위 테스트(`belowMin` `true`) + 컴포넌트 테스트 [제안 후 승인]
- EC-6: EC-5의 경우 결과 카드에 `⚠ 최소 주문 수량은 {formatCoinQty(minOrderQty, qtyStep)} {baseCoin}입니다.`(예: `0.1 SOL`)가 표시되고 한도 경고는 표시되지 않는다 — 검증: 컴포넌트 테스트 [제안 후 승인]
- EC-7: 포지션 가치가 한도와 정확히 같으면(예: BTCUSDT, 레버리지 10, 진입가 100000, 잔고 30000 → 3 BTC, 300,000.00 USDT) 한도 경고는 표시되지 않는다 — 검증: 컴포넌트 테스트 [제안 후 승인]

### 5.3 입력 상태 전환
- EC-8: 심볼을 바꾸면 입력값은 유지되고 새 심볼의 `qtyStep`·`minOrderQty`·`riskLimitValue`·`baseCoin`으로 결과와 경고가 다시 계산·표시된다 — 검증: 컴포넌트 테스트 [제안 후 승인]
- EC-9: 입력을 지워 계산할 수 없게 되면 두 결과가 `—`로 돌아가고 EC-6·DoD-9의 경고도 사라진다 — 검증: 컴포넌트 테스트 [제안 후 승인]
